# ADR 0009 — 影视域合并:电影与剧集不再分库

- 状态: 已接受(2026-11-04)
- 前情: [ADR 0008](0008-扩域-影视库.md)(扩域影视库, 决策 2 定义了 `av` / `movie` / `tv` 三种库域)
- 影响: `libraries.domain` 取值从 `av|movie|tv` 收敛为 `av|video`; 迁移 v11 把历史值改成 `video`

## 背景

ADR 0008 决策 2 把库的域定成三种:番号制、电影、剧集。实现到界面时暴露了两个问题。

**一、类型已经在身份里了。** 影视条目的身份是 `tmdb:tv:1429` / `tmdb:movie:603` ——
"这是剧还是电影"从身份键就能读出来。再让用户在建库时选一遍, 是用一个库级开关
去重复条目级已经确定的事实; 而且这个开关如果选错, 只能删库重建。

**二、同根两库做不到, 而且不该做。** `media_files.path` 是主键, 一个文件只能属于一个库。
所以"同目录放一个电影库和一个剧集库"在数据模型上就不成立 —— 两个库会轮流抢占同一批文件,
各自残缺。而用户盘上的真实情况是:电影和剧混在同一个"影视"目录里。分开建库只在
"电影和剧本来就分开放"时才可行, 那时建两个 `video` 库效果完全一样。

## 决策

**库的域收敛为两个:`av`(番号制)与 `video`(影视)。条目类型仍是三种:`av` / `movie` / `tv`,
但 `movie` 与 `tv` 由身份键推导, 不由库决定。**

推论:

1. `libraries.domain ∈ {av, video}`; `items.domain ∈ {av, movie, tv}`(类型来自身份)。
2. **扫描按目录推断类型**:目录里有文件解析出集号 → 剧目录;一个都没有 → 电影(或还没绑的剧)。
   剧目录里认不出集号的文件不算电影候选, 算"认不出", 等人补集号。
3. **绑定不再校验库与身份种类的匹配**, 只禁止番号制库绑 TMDB 身份 —— 那是两套完全不同的
   识别与来源。影视库里绑 `tmdb:movie:` 就是加一部电影。
4. **想分开管理的人建两个 `video` 库**(根不同即可):`/影视/电影`、`/影视/剧集`。效果与
   分域相同, 但不会出现"同一文件被两家争抢"。
5. 界面上的"影视"是一等概念:建库菜单两项(番号制 / 影视), 侧栏角标「影视」,
   条目级别的差异(季集 vs 单片)由条目自己表达。

## 后果

**得**:
- 建库少一次判断, 而且这个判断事后改不了 —— 少一个不可逆的选择。
- 混放的影视目录可以直接用, 不需要先手工分家。
- 库里不再需要"按域分支"的两套代码(scan/bind/nfo/界面), 只有"按条目类型分支"一套。

**失 / 留给 v2**:
- 整理模板:剧要多一层 `Season {nn}`, 电影不需要。一个库里两种目标目录 = 模板按条目类型
  分支(或引入 `{kind}` 占位符)。organize 在 v2 才做, 届时一并解决; 现在 `video` 的默认
  模板先给 `{series}`。

## 何时推翻

- **真要让一部电影同时属于两个库**(比如"全部影视"+"我的最爱"两个视图)→ 那是**虚拟视图**
  的问题, 不是库的问题:该给筛选/片单, 不要给同一文件两个归属。
- **影视域要按库区分配置**(比如动画库用 Bangumi、日剧库用 TMDB)→ 那时库域需要再细分,
  但应该做成"每个库可选来源", 而不是把类型重新塞回库域。
