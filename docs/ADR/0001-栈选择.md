# ADR 0001 — 桌面壳、core 语言与进程模型

- 状态: 已接受
- 日期: 2026-10-27

## 背景

需求约束(来自使用者):

1. **桌面软件**,给普通人用,不是只有命令行。
2. **带 CLI**,**主要给 agent 调用**。agent 的调用形态是"一次任务 = 一个进程",启动耗时按调用次数相乘。
3. **不做服务端部署**,软件只在被打开时运行;CLI 同样只在执行时运行。
4. 使用者**不懂 Rust**;已有 Vue3 / Java / Kotlin 经验。

候选方案见下表(体积为安装后粗略量级)。

| 方案 | 壳语言 | 体积 | core 语言 | WSL2 交叉出 Windows 包 | 结论 |
|---|---|---|---|---|---|
| Electron | 纯 JS | 150–250MB | 任意 JS/TS | 可以 | **采纳** |
| Tauri v2 | Rust | 5–12MB | 任意(壳是 Rust) | 不支持,需 Windows 机器 | 弃 |
| Wails v2 | Go | 8–20MB | Go | 可以 | 次选 |
| Kotlin Compose Desktop | Kotlin/JVM | ~50MB+JRE | Kotlin | 需目标系统构建 | 弃 |
| Flutter Desktop | Dart | 30–60MB | Dart | 需 Windows 机器 | 弃 |
| PWA + 单文件 exe | 无 | 最小 | 任意 | 可以 | 备选 |

## 决策

### 1. 壳用 Electron

- 渲染进程可以 100% 复用 Vue3 经验,零新语言。
- 主进程就是 Node,core 可以直接在主进程内运行,**不需要额外进程或 HTTP 服务**。
- WSL2 里能做开发,Windows 包能在 WSL 里出(portable 目标不需要 wine)。

放弃 Tauri 的理由不是体积,而是组合成本:**Rust 从零 + WSL 无法交叉到 Windows** 两条叠加,会让"改一个菜单"变成跨机器往返。体积收益(约 200MB)在自用/内部工具里不足以抵偿。

放弃 Kotlin 的理由只有一个但决定性:**CLI 冷启动**。JVM 约 250–400ms,agent 一次任务调 20 次 CLI 就是 5–8 秒纯启动;且 jpackage 必须在目标系统打包。

### 2. core 用 TypeScript,运行在双 runtime 上

同一份 core 被两个宿主加载:

- **Electron 主进程**(Node 内建 `node:sqlite`)
- **CLI 单文件二进制**(Bun 内建 `bun:sqlite`)

两者的 SQLite API 形状不同,差异被 `packages/core/src/db/driver.ts` 一处吸收。**这是本项目唯一为"双 runtime"付出的代价**,换回的是:CLI 无需安装 Node/依赖,20–30ms 启动。

### 3. CLI 用 Bun 编译成单文件二进制

- 实测:100MB(运行时全打包),冷启动 20–30ms,零外部依赖。
- 交叉编译到 Windows 只需 `--target=bun-windows-x64`。
- 若将来无法接受体积:改 Node SEA 或退回 `bun install -g` 分发,`core` 与契约不变。

### 4. 状态用 SQLite,不用守护进程

GUI 与 CLI **不通过 socket 通信**,只共享一个 SQLite 文件:

- `journal_mode = WAL` —— 允许"一写多读"并发。
- `busy_timeout = 5000` —— 写锁竞争时重试而不是立刻 `SQLITE_BUSY`。
- CLI 遇 `SQLITE_BUSY` 映射为退出码 **3(可重试)**。

### 5. 关窗即退出

`window-all-closed` 直接 `close()` + `quit()`,macOS 也不驻留 Dock。单实例锁避免两个 GUI 同时写库。

## 后果

**得**:

- 没有端口、没有鉴权、没有后台常驻、没有进程间协议要维护。
- CLI 与 GUI 的业务行为不可能漂移(core 是同一份)。
- agent 直接 `spawn` CLI 即可,不需要先"启动服务"。

**失(必须接受的代价)**:

- **长任务不能跨窗口存活**:GUI 关了就没了。需要"跑一晚"的任务必须走系统计划任务调用 CLI,或后续加 `--detach`。
- **GUI 不能实时看到 CLI 的写入**。当前实现是操作后重新 `info()`;若要实时,需要文件监听 `kura.db-wal` 或加 `change_log` 表。
- 两个进程同时写时,后写者要等锁(最长 5s)。
- 安装包体积约 150MB+,闲置内存 200MB 量级。

## 何时推翻这个决定

- 需要多人协作 / 手机端同时连同一个库 → 那就需要真的服务端,本 ADR 作废。
- 长任务成为主场景 → 引入独立 worker 进程或计划任务,但 CLI 契约保持不变。
- 体积成为分发瓶颈(如公开下载)→ 重新评估 Tauri,届时 core 无需改动。
