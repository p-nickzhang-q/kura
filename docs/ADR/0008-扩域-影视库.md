# ADR 0008 — 扩域:普通影视(电影 / 剧集 / 动画 / 综艺)

- 状态: 已接受(2026-11-03)
- 前情: [ADR 0002](0002-产品边界.md)(产品边界与可扩展接缝, §1 与「何时推翻」)、[ADR 0003](0003-整理维度.md)、[ADR 0004](0004-翻译.md)、[ADR 0007](0007-演员实体.md)
- 实施细节: [docs/dev/tv-domain.md](../dev/tv-domain.md)

## 背景

用户的盘里不只有番号制 AV,还有普通影视(电影、日剧、国剧、动画、综艺)。
ADR 0002 §1 只承认 `av` 一个域,并留了缝:「扩域时 `items` 表要么加 `domain` 列,要么按域分表」。
现在要决定的是**怎么扩**,而不是要不要扩。

要回答的两个真问题:

1. 普通影视与 AV 是**一个产品**还是**两个产品**(两个 App)?
2. 一部剧是**一个条目**(内含季与集),还是**每季一个条目**、甚至**每集一个条目**?

## 决策

### 1. 一个产品,域在库这一层隔离

一个 App、一个 SQLite、一套 CLI,里面按**库**分域。不做第二个 App,也不抽双壳共享 core。

理由:

- 用户的心智是「我这块盘里有什么」,不是「我现在管 AV 还是管剧」。Emby/Jellyfin 同为多库模型。
- Kura 的差异化能力(字段级来源、字段锁定、翻译、演员实体、NFO 同步、CLI 给 agent 用)与影片类型无关,拆成两个 App 这些都要写第二遍。
- **可逆性**:域在库这一层隔离后,将来真要拆成两个 App,core 已按域分开,拆得开;反过来先拆两个 App 两个库,想合基本合不回来。先合后拆是单向门的安全侧。

代价是产品叙事必须改:「番号制」从产品定语降级为库的一个类型。Kura 这个名字不带番号,不用改名。

### 2. 三种域:`av` / `movie` / `tv`

> **已被 [ADR 0009](0009-影视域合并.md) 收窄**:库的域只剩 `av` / `video` 两种;
> `movie` / `tv` 降级为**条目类型**, 由身份键推导。本节其余内容(域在库这一层隔离、
> 建库时落定、不可跨域转换、同目录不得跨域)仍然有效。

| 域 | 内容 | 身份 |
|---|---|---|
| `av` | 番号制(现有全部能力) | 番号 / 站点键 |
| `movie` | 电影、纪录片、单本剧 | 影视键 `tmdb:movie:<id>` |
| `tv` | 剧集、动画、综艺 | 影视键 `tmdb:tv:<id>` |

- **域是库的属性,建库时落定,不可改。** 选错只能删库重建 —— 只索引库删掉不丢任何磁盘数据,重扫即可。
- `items.domain` 冗余一列(查询与整理模板要用,省 join),权威仍是库。
- **同一个物理目录不得同时被两个域的库引用**,扫描发现重叠直接报错。理由:两个域的整理模板互相冲突,重叠会互相搬家。
- **永不跨域转换**:`av` 条目不会变成影视条目,反之亦然。

### 3. 一部剧就是一个条目,季是集的属性

```
条目(= 一部剧/tv)      tmdb:tv:1399
  └── 集               (season, episode) 剧内唯一
```

- **季不建表、不建身份、不能单独刮削**。季只在剧内部成组显示。没有季概念的剧(多数综艺、部分动画)当作只有一季。
- 用户提过的另一种形态「每季一个条目,里面有集」是**同一份数据的另一种视图** —— 不做两套模型,展示层按需分组(有季的剧在详情页按季分,无季的直接平铺)。

### 4. 影视识别 v1:结构化解析 + 手动目录级绑定

- 只认**结构化目录/文件名**:目录 = 剧,文件名要能解析出集号(`S01E02`、`第02集`、`EP02`、`02`);目录里 `Season 01` / `S01` / `第1季` 解析成季,解析不出季的按第 1 季。
- 解析不出的文件进「未识别」页。用户在那里**按目录**绑定:搜 TMDB 选剧 → 该目录下所有文件一次绑上。
- **不做** TMDB 自动匹配(名字相似度自动选),**不做**视频指纹(OpenSubtitles hash)。
- 验收标准是「能绑定、能刮、能出 NFO」,**不是**「自动识别率高」。

理由:自动选错的危害远大于没选 —— 选错 TMDB id 等于整季集名全错。指纹只对电影有效、要算全库 hash、命中率被字幕版本影响。

### 5. v1 不做 organize

影视库 v1 只有:**扫描 + 刮削 + 集级 NFO 导出**。整理改名(搬到 `{series}/Season {nn}/`)留到 v2。

理由:影视的痛点是「Emby 里显示成一堆 S01E02」,NFO 已经解决 90%;搬家是不可逆动作,在识别还不稳的时候上搬家迟早出事。与 ADR 0002 §5(organize 默认 dry-run)同向:先让人看清单,跑几周没问题再开。

### 6. 影视的 NFO 只写不读

- 剧级一个 `tvshow.nfo`,集级每集一个 `<视频文件名>.nfo`(Kodi/Jellyfin 约定)。
- `nfo sync` 在影视库**只生成/更新,从不回读**。

理由与 `av` 域正好相反:`av` 的 nfo 多是别的工具生成的旧库,所以要能读回来当种子;影视的 nfo 是 **Emby/Jellyfin 会自己写**的(标记已看、自定义集名),回读等于把播放器的内部状态当元数据吸进库里。

### 7. 影视不进翻译层

影视标题/简介/集名**直接取 TMDB 的 `zh-CN` 字段**,缺中文也不机翻。翻译层(ADR 0004)继续只服务 `av` 域。

理由:翻译层存在的理由是「日文源站没有中文」;TMDB 有人工维护的中文,再叠一层机翻等于用劣质译文覆盖官方译文,还会在 `field_sources` 里留下"这条中文是机翻的"这种没人想追的账。

### 8. 演员共用索引,按域标记

- 影视演员进同一个 `actors` 索引,加 `actors.domain` 标记;演员筛选页默认只看当前库的域。
- **只取剧级 cast**(TMDB aggregate credits),不取集级客串。

理由:同一个演员两边都会出现,这正是价值(收藏的演员主演了一部日剧);但集级客串会让一部百集长剧往索引里灌几千个只出现一集的人。

### 9. 刮削任务按剧记账

一次刮削的粒度是**一部剧**(`刮削 第 3/50 部`),内部并发拉剧信息与各季集列表。

理由:一次 TMDB 请求就够拿一部剧的全部集;按集记账会让一次点击产生几百个任务项;而且失败是整部剧失败(剧没找到,集无从谈起),按集重试没有意义。

### 10. CLI:只有建库和跨库查询带域参数

- `library add --domain tv`
- `item list --domain tv`(跨库查询)
- `source test tmdb`
- **`scan` / `scrape` / `organize` 不带域参数** —— 它们是「按库执行」的,库自带域。再加一次等于给 agent 两个可能矛盾的口径。

## 明确不做

| 不做 | 理由 |
|---|---|
| 字幕管理(下载/重命名/校验) | 与"元数据与文件整理"不是一件事,成本却翻倍 |
| 多版本区分(1080p/4K/HDR/导演剪辑) | 同一集就是同一集;重复文件按现有文件相位逻辑处理 |
| 合集 / 花絮 / 特典 | 按现有辅助媒体规则**跳过**,不登记 |
| 剧集重排(absolute / DVD order) | 只认 aired order;重排是独立的判断题 |
| 跨域转换 | 见决策 2 |
| 自动匹配 / 视频指纹 | 见决策 4 |
| 影视的机翻 | 见决策 7 |

## 后果

**得**:
- 一个工具管全盘,用户不用在两个软件之间同步习惯与数据库。
- `av` 域代码路径几乎不动(域在库这一层拦下),3885 条现有条目零回归风险。
- 影视域可以长期停在"够用"档,不追求 tinyMediaManager 的完整度 —— 这是「不做清单」换来的。

**失**:
- 产品叙事要改:「番号制」降级为库类型,README 与简介要重写。
- 扫描/识别/整理永久存在两套规则,每次改动都要问「另一个域受不受影响」。
- 影视识别率注定不满:命名混乱的综艺、年份缺失的老片会大批留在未识别页,需要人工绑定。这是本类产品的固有成本,不是设计缺陷。

## 何时推翻

- **影视域要 organize(改名搬家)** → 新写 ADR,补齐模板与「整季一起搬」的安全规则;不要顺手加进 `organize`。
- **要自动识别(名字匹配或指纹)** → 先有足够真实样本量出误判率,再决定要不要;没有误判率数据的自动识别不许上线。
- **两个域开始互相污染(字段、模板、界面判断到处 if domain)** → 说明该拆进程了,届时回到决策 1 重估。
- **要真正的剧集库管理与播放进度** → 那是媒体服务器(Jellyfin)的活,不是本产品;ADR 0002 的产品定义仍有效。
