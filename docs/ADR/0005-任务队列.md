# ADR 0005 — 持久化任务队列（最小版）

- 状态: 已接受(2026-10-30)
- 前情: [ADR 0002](0002-产品边界.md)(明确"v0.1 不做任务系统")、[ADR 0001](0001-栈选择.md)(无守护进程)

## 背景

实际使用时暴露了两个问题: 批量刮削 200 条要十几分钟，**没有任何反馈**；关掉软件后**不知道跑到哪、也没法继续**。
Amane 用完整的任务系统解决（`Task` 表 + 任务树 + Worker + cancel/retry + 每任务日志 + 前端任务页）。
我们当初砍掉了它，代价就是这两个问题。

## 决策

只补"能回答一个问题"的最小集合：**关掉再打开，我知道跑到哪、并且能继续**。

| 做 | 不做（明确砍掉） |
|---|---|
| `tasks` 表（type/status/payload/progress/error/时间/owner_pid） | 任务树 `TaskLink` |
| 进程内运行 + 逐条进度落库 | 常驻 worker / 守护进程 |
| 取消（运行中走 AbortSignal，排队中直接取消） | 优先级 / 并发调度 |
| 重试（同 payload 新建任务） | 链式派生（SCRAPE→ORGANIZE） |
| 启动时把"宿主已死"的 running 标成 `interrupted` | 跨机器/跨用户任务 |
| 每任务 JSONL 日志 + 脱敏 | 日志检索 / 结构化查询 |

### 为什么没有常驻 worker

与 ADR 0001 的"只在执行时运行"直接冲突。任务由 CLI/GUI 在**当前进程**里跑；进程没了任务就没了，
下次启动靠 `interrupted` 状态告诉人"上次断了"，`task retry` 再跑一遍。
`scrape --pending` 本身是幂等的（只挑没有标题的条目），所以重跑天然就是"继续"。

### 为什么用 `owner_pid` 判断孤儿

GUI 正在跑任务时，另一个终端执行 `kura task list` 也会打开同一个库。
若无条件把 `running` 全标成 `interrupted`，就会把正在跑的任务误杀。
所以只回收"宿主进程已不存在"（`process.kill(pid, 0)` 失败）的那些。

### 日志

`dataDir/logs/tasks/<id>-<时间戳>-<type>.jsonl`：start / 每条进度 / error / end。
写入前统一脱敏（`sk-*`、Bearer、api_key=…）—— 日志经常被贴进 issue。
日志是文件而不是只有 DB：数据库坏掉时它仍然存在，且可以直接 `tail`。

## 后果

**得**：中断可见、可重试、有进度、有日志；CLI 与 GUI 共用同一套（`scrapePendingTask`）。

**失**：任务不能跨进程执行，也没有真正的"暂停/继续"（只有"重跑"）。
没有任务树，所以"刮完自动整理"这类链式动作仍要手工触发。

## 何时推翻

- **要"刮完自动整理"或定时任务** → 需要真正的 worker + 后继边，本 ADR 与 ADR 0002 第 6 条一起改。
- **要真正的暂停/继续** → 需要把逐条游标落库并在恢复时跳过已完成项（当前靠"只挑没标题的条目"近似）。
